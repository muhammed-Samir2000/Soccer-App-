# V1 Application Audit - 2026-09-29

## Verified baseline

- Stack: Flutter/Dart client, Supabase Auth/Postgres/RLS/RPC, Docker/Nginx web image.
- Quality commands: `flutter analyze` completed with no issues; `flutter test --reporter compact` completed with 55 passing tests.
- Scope of the automated suite: domain, mock repositories, Supabase mapping and widget flows. It does **not** exercise a live Supabase project, two authenticated browser accounts, Android, Docker, or push delivery.

## Architecture snapshot

- `AppDependencies.fromBackend` swaps Auth, slot, booking, venue-profile and venue-settings contracts to Supabase when runtime public configuration is present.
- Database RPCs own booking creation, server price calculation, field allocation, operating-hour checks and the overlap exclusion constraint.
- Staff administration, match RSVP and results have Supabase adapters behind
  pending migrations; notification delivery remains in-memory only.

## Release decision

**NO-GO for a public V1 today.** The code has a sound booking-RPC direction and passing unit/widget tests, but it lacks applied/verified security migrations, persistent staff/match/notification functionality, real E2E coverage, Android release signing, monitoring and a backup/restore rehearsal.

## Controlled release path

1. Back up the Staging database and apply the pending migrations in timestamp order, including `20260929100000_harden_direct_write_paths.sql`.
2. Apply and live-test the staff and match adapters; implement or explicitly remove mock-only notification functions from the production navigation.
3. Run and record the live two-account security and booking acceptance matrix.
4. Fix Android signing/build, configure monitoring, document backup/restore, and run a controlled pilot before a public launch.
