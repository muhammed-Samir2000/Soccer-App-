# Decisions Log

## Current Decisions
- Ball is included by default and is not an optional service.
- Optional services are limited to drinks, photography, and referee.
- MVP excludes notifications.
- MVP uses basic or manual payment.
- Only two user roles exist: player and admin.
- Flutter and Dart are the only active implementation stack; legacy React Native references are obsolete.
- Mock repositories are required before any real Supabase integration.
- All user-facing application copy must use Egyptian Arabic, with right-to-left layout and Arabic-Egypt locale settings.
- The player slot picker shows a seven-day week. Matching bookings are assigned to the first free field among fields 1-3 by the repository; a real backend must enforce the same rule atomically.
- Tentative and recurring bookings, staff permissions, and notification preferences are supported in mock mode. OTP delivery, QR rendering/scanning, and push delivery are intentionally not connected.
- The operational week starts on Saturday. The admin starts on a weekly availability summary, opens a day for its available hours, and manages existing bookings from a separate management section.
- GitHub versioning is mandatory for every completed user-requested change set: verify, commit with a descriptive message, push to `origin/main`, and record the resulting commit in the workflow log. Generated builds, local logs, and secrets must remain excluded.
- Flutter is the active UI layer: RTL is implemented through Flutter directionality and directional layout APIs, not CSS. Shared navigation uses a left-facing, Arabic-labelled back action. Slot repositories expose a watch stream so a future Supabase/WebSocket implementation can publish live availability.
- An admin registers a player from a specific available hour, instead of manually re-entering that hour. The reception flow requires a player or group name and phone number, lets the admin choose `مؤكد` or `مبدئي`, and delegates identical-field allocation to the booking repository.
- The admin registration form separates booking state from repetition intent: `مؤكد` or `مبدئي` applies to a one-off booking, while `ثابت` records the booking as recurring in the existing mock domain. `لمرة` keeps the selected state for one appointment.
- Admin day selection uses one shared Arabic calendar control in quick/fixed booking and booking editing. In mock mode it is constrained to the operational Saturday-to-Friday week; backend scheduling will later supply the valid date range.
- The public entry screen is player-only and offers Google or email/password choices, with no role selector and no SMS cost. Authentication returns the account role; Flutter never submits a requested role to the provider. The interface is mock-only until a real provider verifies the account and returns its role.
- Venue settings are isolated in a repository: configurable field count and opening/closing hours drive the admin occupancy dashboard, day availability, and quick bookings. Lowering capacity is rejected when an existing booking uses a now-removed field.
- The visual system uses an emerald football-club palette with a restrained warm accent, strong summary cards for player availability and admin occupancy, and shared component theming. Arabic labels and booking states remain the primary way to communicate meaning; color is supportive rather than the only signal.
- The public entry point is player-only and does not expose an admin-role switch. Admin access has a separate route and is guarded by the active role; an authoritative backend must later enforce the same rule for every API request and database policy.
- Admin accounts are invitation-only: no self-service admin registration exists. A future owner-managed backend must create an invitation, assign a venue-specific role, and reject any identity not granted that role.
- Financial analytics derives collected revenue from confirmed and recurring bookings, excludes tentative bookings, and compares a selected month range with the immediately preceding range of equal length. Until payment records exist, this is an operational estimate rather than a settlement report.
- The admin mobile shell uses a persistent Material 3 bottom navigation bar for Dashboard, Bookings, Finance, and Settings. The high-frequency quick/fixed booking task stays in a floating action button above it; staff permissions and notification controls remain secondary settings actions.
- The trial build uses direct demo entry for player and admin without collecting credentials. This bypass exists only in the mock client and must be removed when real authentication is approved.
- Notifications are now in-app mock notifications. Booking activities generate manager notices with player name, phone number, services, and confirm/edit/cancel actions. Player notices show available slots for the demo day and the following day with booking actions. No push, SMS, WhatsApp, or scheduled delivery is connected.
- Supabase preparation uses a staging-first SQL migration with RLS enabled on every application table. Players have no direct booking insert permission; a future authenticated booking RPC must validate capacity, price, and services server-side. Super-admin promotion is an administrative service-role process and never a Flutter client capability.
- A confirmed booking can own one optional group match. The organizer starts as `جاي`; player capacity defaults to 10 but remains configurable from 2 to 30, because field formats vary. RSVP never cancels or invalidates the field booking when the team is incomplete.
- Group invitations expose only match-level details and player display names. Phone numbers, email addresses, user identifiers, and the invitation-token hash are never shown to participants. The mock link is explicitly demo-only; production creates a high-entropy token server-side, stores only its SHA-256 hash, supports expiry/revocation, and accepts RSVP through an authenticated RPC that serializes capacity checks.
- A teammate must authenticate before recording `جاي` or `مش جاي`. The current Google action is a mock entry only; real Google OAuth requires explicit Supabase Auth configuration, redirect URLs, authenticated repository adapters, and RLS acceptance testing. Transactional invitations/reminders and optional vacant-slot marketing must use separate, explicit notification consent.
- Live Staging authentication presents a labelled Google action in both player and admin entry screens. Admin OAuth is invitation-only: a Google-authenticated profile without an `admin` or `super_admin` platform role is signed out and denied the admin route.
- Admin-team access uses an approved e-mail allowlist per venue. A manager can prepare a `manager` or `reception` invitation with booking and financial permissions, but the Flutter client cannot promote a profile directly or create a `super_admin`. A security-definer Supabase RPC consumes a pending invitation only after the signed Google JWT e-mail matches it exactly.
- During the staged transition, the active authenticated player's ID and display name are explicit inputs to the mock booking contract so the local confirmation-to-`حجوزاتي` journey remains coherent. This is not a production trust boundary: the future Supabase booking RPC must derive ownership from `auth.uid()` and ignore any client-supplied owner identity.
- A persisted Google session must not silently enter the player experience. The entry screen identifies the saved account and requires an explicit continue action, while offering sign-out for account switching. Navigation shows a back action only when a prior route exists.
- Live player and admin access use Google OAuth only. Demo login remains test-only when no backend configuration is supplied and must never be enabled for a deployed build.
- `super_admin` is a distinct server-owned role. Only that role may manage team invitations, contact data, permissions, or revocation. The first super-admin is provisioned by a controlled server-side operation after Google identity verification; neither the Flutter client nor an ordinary admin can create or promote one.
- Operating hours describe an operational day, not necessarily one calendar day. A closing hour earlier than the opening hour means closing on the next calendar day; for example, `15:00` to `02:00` exposes eleven bookable hourly slots and assigns `00:00` and `01:00` to the prior evening's operating day. Equal hours are invalid.
